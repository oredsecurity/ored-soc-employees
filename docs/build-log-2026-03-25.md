### New Lesson: Windows netsh Dispatch Is Not Enough

The March test proved `netsh.exe` can create a Windows firewall block when dispatched by Wazuh. The June 17 retest added the missing rollback proof.

Result: API-triggered `netsh` rollback was not reliable. The Wazuh API path sent another `add` operation with `delete` as an argument, and the Windows firewall block remained until manually removed from an elevated PowerShell session.

Manual cleanup command used:

```powershell
netsh advfirewall firewall delete rule name="WAZUH ACTIVE RESPONSE BLOCKED IP" remoteip=203.0.113.10/32
```

### Decision

Windows IP blocking is now fail-closed in ARGOS until we implement a custom reversible Windows wrapper. Linux built-in response remains allowed where supported. Do not re-enable Windows `netsh` response until this full chain passes:

1. Add block.
2. Verify block exists.
3. Delete block.
4. Verify block is gone.
5. Confirm Wazuh audit evidence for each step.


## Update: 2026-06-17 Windows Active Response Wrapper

Step 5 begins replacing unsafe Windows `netsh.exe` dispatch with a custom reversible wrapper named `ored-win-firewall`.

### Design

- Windows IP block/unblock will map to `!netsh` only after the Wazuh active-response `netsh.exe` slot is replaced by the ORED native wrapper carrier.
- The wrapper accepts explicit `action=add`, `action=delete`, and `action=status` arguments.
- The wrapper owns only firewall rules named `ORED ARGOS BLOCKED IP`.
- Add and delete verify final Windows firewall state before exiting.
- Built-in `netsh` remains blocked in generic active response.

### Files

- `scripts/active-response/windows/ored-win-firewall-native.c`
- `scripts/active-response/windows/ored-win-firewall.exe`
- `docs/windows-active-response-wrapper.md`

### Required Live Test

The wrapper is not trusted until it passes the live add/delete chain on `001 / ored-win-01` and leaves no firewall rule behind.

### Live Test Finding

The wrapper is built but not yet production-trusted. Wazuh API accepted custom commands and returned `affected_items: ["001"]`, but the Windows agent did not launch the custom command. Built-in `!netsh` still launched, proving the manager-to-agent active-response channel works.

Findings:

- `.cmd` launcher produced agent error `(1317): Could not launch command No error (0)`.
- `.exe` launcher installed successfully, but custom `!ored-win-firewall`, `!oredfw`, and `!oredfw.exe` calls were accepted by the API without endpoint execution evidence.
- Endpoint firewall state remained unchanged and `active-responses.log` had no wrapper entries.
- ARGOS must remain fail-closed for Windows IP response until custom dispatch is solved.


### Native Carrier Attempt

A native Windows wrapper was added after the `.cmd` and .NET launcher approaches failed to produce endpoint execution evidence. The intended practical install path is to back up Wazuh's launchable active-response `netsh.exe` as `netsh.wazuh-original.exe`, then replace `netsh.exe` with the ORED native wrapper. This keeps the known Wazuh command slot but changes endpoint behavior to explicit `action=add` and `action=delete` handling.

Current status: native wrapper is built in the repo, but installation into `C:\Program Files (x86)\ossec-agent\active-response\bin` needs elevated Windows approval. Live add/delete validation is still pending.

### Live Test Update: Protocol-Aware Wrapper Passed

The wrapper was updated to implement Wazuh's custom active-response protocol:

- read the first JSON payload from stdin;
- emit `check_keys` to stdout;
- wait for Wazuh's `continue` response;
- use action-specific keys: `ored-win-firewall:add:<ip>` and `ored-win-firewall:delete:<ip>`.

Result on `001 / ored-win-01`:

- `!ored-win-firewall-v3` added `ORED ARGOS BLOCKED IP` for `203.0.113.80`.
- Endpoint firewall state confirmed the rule existed.
- Wrapper log confirmed `add srcip=203.0.113.80 rc=0`.
- `!ored-win-firewall-rollback` removed the same rule.
- Endpoint firewall state confirmed no `ORED ARGOS BLOCKED IP` rule remained.
- Wrapper log confirmed `delete srcip=203.0.113.80 rc=0`.

Decision update: Windows IP containment can be wired into ARGOS high-level guarded tools using `!ored-win-firewall-v3` for block and `!ored-win-firewall-rollback` for allow. Generic raw `netsh` and arbitrary Windows active-response commands remain blocked.


### Live Test Update: Final June 17 Safety Reset

- The endpoint was reset after testing so no `ORED ARGOS BLOCKED IP` rules remained.

Product decision: Windows IP containment can be enabled through ARGOS high-level guarded tools after human approval. Generic raw `netsh` and arbitrary Windows active-response commands remain blocked.
